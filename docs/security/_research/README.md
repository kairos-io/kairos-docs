# CIS control matrix - research material (kairos-io/kairos#4628)

Working notes behind the CIS control matrix page. Not published.

## Why this lives here

Docusaurus' docs plugin excludes `**/_*/**` by default, so an underscore-prefixed
directory inside `docs/` is scaffolding rather than content: nothing in here is picked up
by the autogenerated sidebar (`sidebars.ts` uses `{type: 'autogenerated', dirName: '.'}`),
and nothing in here gets a URL. That keeps the raw material next to the page it feeds
without shipping a half-finished matrix to the site.

If the material stops being useful once the page lands, delete the directory; the page is
the deliverable.

## Sourcing

No CIS benchmark PDF text is reproduced. Control IDs and check descriptions come from two
Apache-2.0 projects that implement the benchmarks as automated checks:

- `aquasecurity/kube-bench`, `cfg/cis-1.9/` (five role files: `master`, `etcd`,
  `controlplane`, `node`, `policies`)
- `dev-sec/linux-baseline`, `controls/` (three InSpec files: `os_spec.rb`,
  `package_spec.rb`, `sysctl_spec.rb`)

Both fetched from their default branches on 2026-09-15. Titles and intents are restated,
not copied from CIS.

Each file opens with a caveat section on what its source does and does not let us claim.
Both caveats are load-bearing and neither should be dropped when composing the page:

- kube-bench encodes **no CIS profile level**, so the Level 1 subset is not derivable and
  is not guessed at.
- dev-sec/linux-baseline encodes **no CIS control IDs at all**, so that table is keyed on
  devsec IDs and maps to CIS numbering in only three cases.

## Status determinations

Evidence was gathered by reading `kairos-io/kairos` at `upstream/master` (tip `dac37dc4`)
plus the unmerged branch `triage/4626-cis-l1-initial-setup` (PR #4650, tip `9d0b3b8e`).
Every `Implemented` row cites a file and line range that was actually read. Where the
implementation could not be located, the row is `Open`, not a guess.

`Not applicable` is used narrowly: only where the control's target artifact does not exist
on a Kairos node (kubeadm static pod manifests under k3s/k0s), or where satisfying it would
break the product (`kernel.modules_disabled=1`, `ip_forward=0` on a Kubernetes node).
"Kairos happens not to install this package" is `Open`, not `Not applicable`.

## Four things to settle before publishing

1. **PR #4650 is not merged.** The three CIS DIL sections Kairos cites in its own code
   (1.1.1.x, 1.7, 6.1) live only on `triage/4626-cis-l1-initial-setup`. No released image
   has them. The page must either wait for the merge or gate those rows behind a version
   note. Details and the verifying commands are in `linux-baseline-l1-controls.md`.

2. **The Kubernetes table has zero `Implemented` rows, by construction.** Kairos installs
   k3s/k0s from their own installers and sets no CIS-relevant Kubernetes flag; grep for
   `protect-kernel-defaults`, `tls-cipher-suites`, `anonymous-auth`, `audit-log` and
   `secrets-encryption` across the repo returns nothing. The honest page says the
   Kubernetes benchmark is operator territory and points at the `k3s.args` / `k0s.args`
   passthrough, rather than implying coverage Kairos does not have. That is a bigger
   editorial decision than a table cell and wants a maintainer's eye.

3. **Side finding, not fixed here.** `kairos-init/pkg/bundled/cloudconfigs/10_accounting.yaml:31`
   spells the yip file-mode key `permsisions: 0600` instead of `permissions: 0600`, so the
   mode is silently dropped and `/etc/sudoers` is written with whatever yip defaults to.
   That is directly in scope for CIS DIL section 6.1, which this matrix documents. It is a
   one-character production-code fix in a different repo than this ticket's deliverable, so
   it belongs in its own kairos-io/kairos issue rather than smuggled into a docs PR.

4. **Verification pass (tester, round 0): dataset holds up, with one fixed citation and a
   minor systemic imprecision to watch.** ~25 citations were independently re-read against
   `upstream/master` (tip `dac37dc4`) and `triage/4626-cis-l1-initial-setup` (tip `9d0b3b8e`,
   confirmed NOT-MERGED again independently), covering every `Not applicable` row's
   "artifact does not exist" claim, all three `Implemented (unmerged)` rows, both
   `os_spec.rb`/`sysctl_spec.rb` product-incompatibility NAs, and all eight negative-grep
   `Open` claims (`hosts.equiv`, `login.defs`, `telnet`, `ypserv`, `tftp`, `prelink`,
   `ip_forward`, `rsh-server` all reconfirmed empty). Every factual claim checked out.
   One citation was wrong and has been corrected in `linux-baseline-l1-controls.md`:
   `os-03b` pointed at `10_accounting.yaml:19` for the `kairos` user's `passwd: "!"` line;
   the line is actually `:14` (`:19` is the start of an unrelated adjacent stage). Separately,
   the `steps_cis_hardening.go` line pointers in `os-02`/`os-03`/`os-10` run 1-2 lines short
   throughout (e.g. the `test -f` guard cited as `:97` is actually `:99`) - content at each
   citation is still correct, just the exact line number drifts by a small constant. Not
   worth a row-by-row fix; a reviewer diffing against the branch should expect a small offset
   rather than treat it as a wrong citation.
